# 📖 AI 駆動開発プレイブック

> 本プロジェクトで実践した **twin-build フロー** + **AI 共同開発** の知見を、
> **次の案件で再利用できる形** に汎用化したプレイブック。
> セールスエンジニア / AI コンサル目線で「クライアントに同じやり方で進められるか」を判断する材料にも。

---

## 1. AI 駆動開発とは(1 行)

> **「人間が判断、AI が生成・実装」を、フェーズゲートで構造化した開発スタイル**

| 要素 | 従来開発 | AI 駆動開発 |
|---|---|---|
| 仕様策定 | 人間が書く | **AI が対話で引き出し、人間が判断** |
| コード生成 | 人間が書く | **AI が生成、人間がレビュー** |
| 設計整合性 | 人間が頑張る | **Coverage で機械的に検証** |
| フェーズ移行 | 暗黙的 | **Gate で意思決定を記録** |
| 速度 | 人間の手作業に依存 | **数倍〜10 倍速** |

## 2. AI 駆動開発の 5 原則(MoveMap プロジェクトから抽出)

### 🟢 原則 1: 「フェーズゲートを守る」

各フェーズの成果物が前フェーズに整合していることを確認してから次に進む。

**実例**: Phase 0(課題) → Phase 1(要求) → ... → Phase 8(レビュー)
- Phase 1 を始める前に Phase 0 の「課題」が明確か確認
- Coverage(設計と実装の整合性メトリクス)を可視化

**やってはいけないこと**:
- フェーズを飛ばす(例: 課題定義なしで設計に入る)
- AI が生成した設計を読まずに次フェーズへ

### 🟢 原則 2: 「AI に任せること / 人間が判断することを分ける」

| AI に任せる | 人間が判断 |
|---|---|
| コード生成 | 技術スタック選定 |
| ドキュメント作成 | プロダクト戦略 |
| テスト書く | ペルソナ定義 |
| ライブラリ調査 | 課金プラン設計 |
| エラーメッセージ解読 | セキュリティ判断 |
| パターン適用 | データソース信頼性評価 |
| 単純なリファクタ | 競合差別化 |
| 命名提案 | API キーの貼付 / 公開判断 |

**実例**:
- Streamlit を選んだのは人間判断、各 Usecase の実装は AI
- reinfolib API がダメだと分かった時の「賃料ソース切り替え」は人間判断、新アダプタの実装は AI

### 🟢 原則 3: 「1 件 probe してから本実装」

外部 API / ライブラリ / フレームワーク を使う時、**まず 1 件叩いてレスポンス・挙動を確認** してからコード化する。

**実例**:
- e-Stat の `0003411634` を「都道府県別出生数」と想定 → 1 件 probe で **全国計のみ** と判明 → `0003412062` に変更
- reinfolib `XCT001` を「賃料指数」と想定 → 実は **地価公示** だった → 別 API 探索

**実装パターン**:
```python
# Step 1: 1 件 probe
def probe():
    r = requests.get(URL, params={"id": "test"})
    print(r.json())  # 中身を目で確認

# Step 2: probe 結果を元にパーサ設計
# Step 3: 単体テストでパーサ検証
# Step 4: 結合テストで DB 連携
```

### 🟢 原則 4: 「動くものを 1 周作ってから磨く」

最小限の機能で **End-to-End 動く状態** を最速で作り、そこから改善する。

**実例**:
1. ダミーデータで 47 都道府県 MAP が動く ← まずここ
2. 実 API 連携(1 ソースずつ)
3. UI/UX 改善
4. スマホ対応
5. 課金プラン検討

**やってはいけないこと**:
- 完璧な設計を求めて実装に入らない
- 全機能揃うまでデプロイしない

### 🟢 原則 5: 「透明性を組み込む」

ユーザーが「データが嘘か本当か」を **自分で判断できる材料** を UI に組み込む。

**実例**:
- データ鮮度表示(🔵 DB 実データ / 🟡 ダミー)
- 最終更新日表示
- 出典明記(e-Stat / 国交省 / WAQI)
- AI モデルの R² と学習日時(モデル根拠タブ)
- 予測対象外都道府県の灰色表示 + 件数キャプション

「**信頼は透明性から生まれる**」がこのプロジェクト全体の柱。

## 3. Phase 0-8 各フェーズのチェックリスト

### Phase 0: 課題定義(問題発見)

**目的**: 「誰の何の問題を解くか」を 1 文で言える状態にする

**チェックリスト**:
- [ ] ターゲット顧客は誰か?(1 ペルソナ + 補助 1-2 ペルソナ)
- [ ] 顧客の現状の不満 / 不便 / 諦めは何か?
- [ ] その問題が解けると、顧客にどんな価値が生まれるか?
- [ ] 既存の代替手段は何か?(競合 / DIY / 諦め)
- [ ] 問題の規模感(N 万人 / N 億円市場)

**AI への指示テンプレ**:
> 「以下のテーマで、ターゲット顧客 / 痛み / 価値 / 代替手段 / 規模感の 5 項目を整理してください: [テーマ]」

**成果物**: `outputs/00_problem.md`(1-2 ページ)

---

### Phase 1: 要求仕様

**目的**: Must / Should / Could を明確化し、優先度を決める

**チェックリスト**:
- [ ] Must(これがないとプロダクトと言えない)が 5-10 個
- [ ] Should(あれば価値が大きい)が 5-10 個
- [ ] Could(あったら最高、後回し可)が 5-10 個
- [ ] 各要件に **検証可能な完了条件**(Acceptance Criteria)

**AI への指示テンプレ**:
> 「Phase 0 の課題に対し、Must/Should/Could に分けて 15-25 個の要件を出してください。各要件に Acceptance Criteria を 1-3 個付けてください」

**注意点**: AI は「全部 Must」にしがち → 人間が削る

**成果物**: `outputs/01_requirements.md`

---

### Phase 2: 業務構造

**目的**: 登場人物(エンティティ)と関係性を整理

**チェックリスト**:
- [ ] エンティティ一覧(オブジェクト / アクター)
- [ ] エンティティ間の関係(所有 / 参照 / 集約)
- [ ] 各エンティティの主要属性
- [ ] 不変条件(INV)の候補

**成果物**: `outputs/02_business_structure.md` + ER 図(Mermaid)

---

### Phase 3: 業務フロー

**目的**: ユーザーがどう操作するか、データがどう流れるか

**チェックリスト**:
- [ ] ユーザーシナリオ(Happy Path + Error Path)
- [ ] データフロー図
- [ ] 月次 / 日次バッチ等の自動処理フロー
- [ ] 例外処理(外部 API 失敗 / DB 故障 / 認証失敗 等)

**成果物**: `outputs/03_business_flow.md` + シーケンス図

---

### Phase 4: システム要件

**目的**: 非機能要件(性能 / セキュリティ / 可用性 / 保守性)を明確化

**チェックリスト**:
- [ ] 性能(ページロード時間、同時接続数)
- [ ] 可用性(SLA、ダウンタイム許容)
- [ ] セキュリティ(認証、認可、暗号化、監査ログ)
- [ ] スケーラビリティ(ユーザー増加時の対応)
- [ ] 保守性(ログ / モニタリング / バックアップ)
- [ ] **不変条件(INV)を確定**

**成果物**: `outputs/04_system_requirements.md` + `outputs/baseline.md`(INV 一覧)

---

### Phase 5: アーキテクチャ

**目的**: 技術スタック選定と全体構造

**チェックリスト**:
- [ ] 言語 / フレームワーク(理由付き)
- [ ] データストア(理由付き)
- [ ] 外部サービス連携
- [ ] デプロイ環境
- [ ] フォルダ構造(VSA か レイヤーアーキか)
- [ ] **代替案を 1-2 個** 出して比較表で記録

**AI への指示テンプレ**:
> 「以下の要件に対する技術スタック候補を 2-3 個出し、メリット / デメリット / コスト / 学習曲線で比較表を作ってください: [要件サマリ]」

**注意点**: AI は「流行りのスタック」を提案しがち → 人間がチームのスキルセット・運用コストで判断

**成果物**: `outputs/05_architecture.md`

---

### Phase 6: システム設計

**目的**: 詳細設計(画面 / API / データ / 状態遷移 / シーケンス / テスト)

**チェックリスト**:
- [ ] 画面設計(SCR-XXX 番号付き、ワイヤーフレーム)
- [ ] API 設計(エンドポイント、リクエスト / レスポンス)
- [ ] データ設計(テーブル、CHECK 制約、FK)
- [ ] 状態遷移(注文 / バッチ / ユーザーの状態マシン)
- [ ] シーケンス図(主要フロー)
- [ ] テスト設計(TC-XXX 番号付き、Must カバレッジ確認)

**成果物**: `outputs/06_system_design/` 配下に複数ファイル

---

### Phase 7: 実装

**目的**: 設計通りに動くコードを書く + テスト

**チェックリスト**:
- [ ] 各 Usecase の impl が完成
- [ ] 各 Usecase の impl_test が完成
- [ ] Coverage(設計 ↔ 実装 ↔ テスト)が 100% 近い
- [ ] CI(GitHub Actions)が緑
- [ ] **`/review` 評価が B+ 以上**

**AI への指示テンプレ**:
> 「Phase 6 の設計書を読んで、[Usecase 名] の impl と impl_test を生成してください。
> 既存コードの命名・パターンに合わせてください。
> テストは正常系 + 異常系 + エッジケースを各 1-2 個」

**成果物**: `app/` 配下 + `tests/` 配下

---

### Phase 8: レビュー

**目的**: 最終チェック + 振り返り + 次フェーズへの引き継ぎ

**チェックリスト**:
- [ ] **`/review` 評価**(consistency / expert / risk / business)
- [ ] セキュリティチェック(OWASP / 依存脆弱性)
- [ ] パフォーマンステスト
- [ ] 残課題・持ち越しの明確化
- [ ] 次に着手する Top 3 タスク決定

**成果物**: `outputs/99_review.md`

## 4. 「AI に任せる」のレベル分け

```
レベル 0: 何もない(全部人間)
レベル 1: AI に質問する(壁打ち)
レベル 2: AI にコード片を書かせる(snippet)
レベル 3: AI に Usecase 単位で書かせる(機能単位)  ← MoveMap 現状
レベル 4: AI に Phase 単位で書かせる(設計 + 実装 + テスト)
レベル 5: AI 完全自律(目標を与えるだけ)
```

**MoveMap の現状**: レベル 3-4 のハイブリッド
- 各 Usecase は AI が生成 → 人間がレビュー
- 設計書も AI が雛形を生成 → 人間が意思決定
- 重要な判断(技術選定 / 課金プラン / セキュリティ)は人間

## 5. つまずきポイント TOP 10(MoveMap から)

### #1: API 仕様と実レスポンスの乖離

**例**: reinfolib XCT001 が「不動産価格指数」想定 → 実は地価公示
**対策**: 必ず 1 件 probe してから本実装

### #2: 文字コード問題(Windows cp932)

**例**: `R²` を logger に出力すると UnicodeEncodeError
**対策**: ログ出力は ASCII 化 OR `sys.stdout.reconfigure(encoding="utf-8")`

### #3: API パラメータの型(int vs str)

**例**: reinfolib `area=1`(int)→ 400、`area="01"`(str ゼロパディング)→ 200
**対策**: エラーメッセージを読んで型を疑う

### #4: 外部依存の発行待ち

**例**: reinfolib API キー 5 営業日待ち
**対策**: 並行作業ができるよう設計、フォールバック実装

### #5: ライブラリの非互換変更

**例**: Streamlit `use_container_width` の deprecation
**対策**: 警告は無視せず CHANGELOG を月次確認

### #6: テストが実 API を叩いてしまう

**例**: `__init__(api_key=None)` でも env から実キーを取って実 API を叩く
**対策**: `monkeypatch.delenv` + 明示的 None 上書き

### #7: AI の幻覚(hallucination)

**例**: AI が「e-Stat API には XXX エンドポイントがある」と言うが実在しない
**対策**: AI の出力は **公式ドキュメント or 1 件 probe** で必ず検証

### #8: 設計と実装の乖離

**例**: Phase 6 で「キャッシュする」と決めたが、実装で忘れる
**対策**: Coverage 検証 + Phase 7 完了時の `/review` で機械チェック

### #9: 「ちゃんと動いた」幻想

**例**: テストは通るが、UI で見たら表示崩れ
**対策**: smoke テスト + 必ず手動で UI 確認 + スクリーンショット

### #10: スコープクリープ

**例**: 「ついでに XX も実装しよう」が積み重なって完了しない
**対策**: Must/Should/Could を厳守、Should 以下は別 Phase

## 7. 次案件で再利用するためのテンプレ集

### A. AI への初回指示テンプレ

```
あなたは [役割] です。
これから [プロジェクト名] の Phase [N] を進めます。

【前提】
- Phase [N-1] の成果物: [リンク or 内容]
- 制約: [予算 / 期限 / 技術スタック]
- 私の役割: 判断・レビュー
- あなたの役割: 提案・生成・実装

【今回のゴール】
[Phase N で達成したいこと]

【進め方】
1. まず質問してください(私の情報不足を埋めるため)
2. 質問が解消したら、案を 2-3 個出してください
3. 私が選んだ案に対して、詳細を実装してください

【出力フォーマット】
- 設計: Markdown
- コード: ファイル単位で、フォルダ構造を含める
- テスト: pytest 形式
```

### B. Phase 完了時のチェックリスト(テンプレ)

```
- [ ] 成果物が `outputs/` または `app/` に保存された
- [ ] AI 生成内容を人間が **1 行ずつ** レビューした
- [ ] Coverage が 80% 以上
- [ ] CI が緑
- [ ] 次 Phase への持ち越し論点が記録された(課題 / TODO / RISK)
- [ ] memory に進捗 + 学びを追記
```

### C. AI コンサル文脈で使うフレーズ集

| 状況 | フレーズ |
|---|---|
| 顧客が AI 駆動開発の経験ゼロ | 「最初の 1 案件は教育投資として、私たちが伴走します」 |
| 「AI に全部任せたい」と言われた | 「判断は人間、生成は AI が原則。例えばこんな判断が必要です…」 |
| 「コードレビューする時間がない」 | 「AI が書いたコードを **全件レビュー** より **抜き取り + テスト** で品質担保します」 |
| 「セキュリティ大丈夫?」 | 「依存脆弱性は pip-audit で CI チェック、API キーは .gitignore + .env で隔離、本番は別管理」 |
| 「コストは?」 | 「Claude API 月 $20-100、開発工数 50% 削減で人件費圧縮、ROI は 3 ヶ月で出る想定」 |

## 8. AI 駆動開発を提案する時の「3 つの説得材料」

### 材料 1: スピード

> 「MoveMap は **5 日で 7 タブのアプリ** + AI 予測 + 実 API 連携を完成させました。
> 従来開発なら 2-3 ヶ月かかる規模です」

### 材料 2: 品質

> 「テスト 199 件、Coverage 100%、不変条件 18 件全て検証済み。
> AI に書かせたから雑、ではなく **構造化されているから品質が担保できる** のです」

### 材料 3: 透明性

> 「twin-build フローの Phase 0-8 で **判断の記録** が全部残っています。
> なぜこの技術を選んだか、なぜこの仕様か、後から追えます」

## 9. やってはいけないアンチパターン

### ❌ AI の出力を **読まずに** マージする

→ 必ず 1 行ずつ目を通す。少なくとも diff は全件確認。

### ❌ AI に「全部やって」と丸投げ

→ 判断材料(制約 / 目的 / 前提)を渡さないと意味不明な提案が返ってくる。

### ❌ AI を「議論パートナー」として使わない

→ 「これでいいかな?」と聞かず、「3 つ案を出して比較して」と聞く。

### ❌ コードを残さずチャットだけで完結

→ 必ず Git にコミット、判断は memory / outputs/ に記録。

### ❌ 失敗を隠す

→ AI 駆動でもバグは出る。包み隠さず学びとして書き残す(本ドキュメント #5 のように)。

## 結び: AI 駆動開発の哲学

> **「AI は速い助手、人間は遅い判断者」**
>
> AI に全てを任せてはいけない。
> しかし、判断と方針が決まっているなら、AI は人間の 10 倍速で実装する。
>
> **判断を磨くために時間を使い、実装は AI に任せる。**
> これが AI 時代の開発者の役割。
