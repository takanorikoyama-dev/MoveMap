## 🔑 解答ヒント

### A の解答ヒント

- **A-1**:「全国 47 都道府県を 9 観点で比較・診断・予測できるデータドリブン地方移住検討ツール、個人制作のポートフォリオ」
- **A-2**:① 情報散在 → 統合スコア化、② 判断軸なし → 偏差値 + 加重、③ 将来見えない → AI 予測 3/5/10 年
- **A-3**:↑(高い方が良い):出生数 / 交通アクセス / 人口流入。↓ それ以外 6 指標。
- **A-4**:予測対象 = 主要 4 指標(物価/地価/賃料/出生)+ ARIMA/Prophet で予測可能な時系列性あり。非予測 5 指標 = 観測 / 静的データで、INV-DATA-004 で予測禁止
- **A-5**:9 指標を偏差値化(50 = 平均、SD = 10)→ 住みやすさ方向で反転(↓指標は -1 倍)→ 加重平均。なぜ:単位がバラバラ(円/m² と AQI と件数等)なので正規化が必須

### B の解答ヒント

- **B-1**:① Python 一言語で UI〜ETL〜ML 完結、② 個人開発で最速、③ Streamlit Cloud 無料デプロイ容易。トレードオフ:① SEO に弱い(SPA で初期 HTML が空)、② フロント独自カスタマイズの自由度低い
- **B-2**:利点 = ファイル 1 つで完結 / 大量データ OLAP に強い / Streamlit と相性◎。欠点 = 同時書込み弱い / マルチユーザー認証なし。Cloud ephemeral 問題 = コンテナ再起動で消失 → `seeds/movemap_sample.duckdb` 同梱 + `app/shared/bootstrap.py` で cold start に自動復元
- **B-3**:VSA = 機能(usecase)ごとにフォルダ → 変更影響を局所化。レイヤ別との比較:VSA は機能追加が早い、レイヤ別は再利用しやすい。本プロジェクトは個人開発で変更が機能単位なので VSA 優位
- **B-4**:ARIMA = 線形トレンド + 季節、Prophet = 休日効果 + 変化点。単一だと欠落するパターンがある。アンサンブルで R² を底上げ + R² < 0.6 fallback で安全性確保
- **B-5**:常時表示は離脱率高い + UX 悪い。GA4 未設定 = 計測がない = Cookie 不要 = 表示も不要。**機能の有無に応じて法的要件を満たす設計**
- **B-6**:① `<script>` が DOMPurify で除去される、② JS 駆動の自動スライドが動かない、③ クリックインタラクションが効かない
- **B-7**:背景 = ホーム = ヒーロー + バナーで「ファストビュー」を作りたかった + 全画面ワイドビジュアル。改善 = 第一印象の刷新感、URL でブックマーク可能。犠牲 = サイドバーで提供していた指標 / 時点切替が各 view に内包され UI 微増、ナビが多階層化
- **B-8**:① 初期 HTML が空(コンテンツは WebSocket 経由で後から)、② meta タグを `<head>` に注入不可、③ URL がクエリパラメータ駆動で各 view が独立 URL になりにくい。対応 = 静的 LP(GitHub Pages)を併設

### C の解答ヒント

- **C-1**:データ改変・監査・再現性のため。物理層 = `HistoryProtectedConnection` ラッパで UPDATE/DELETE/TRUNCATE 文を実行時に拒否(DEC-013)
- **C-2**:旧:dummy fallback。新(2026-06-03 修正):current_values × 県別シナリオ年率で外挿。なぜ:サンプル DB / run_batch 未実行環境でも 47 県全部値が入る方が UX 良い + 偏差値ランキングが意味ある計算になる
- **C-3**:① upsert(冪等な INSERT or UPDATE)+ ② append-only history(同じデータ追加でも結果が変わらない)
- **C-4**:絶対件数だと「東京 96k vs 秋田 2k」となり**人口に強く相関**、純粋な治安指標として比較できない。千人率化で人口規模の影響を除外
- **C-5**:`session_state` = 真の状態源(view 切替、Cookie 同意 等)。URL クエリ = 共有・ブックマーク用の表現。同期は `app/main.py` のトップで URL → session_state に一方向統一、混乱回避

### D の解答ヒント

- **D-1**:Phase 1 の専門家レビューで R-01(市場規模)/R-02(リピート性)/R-03(法的リスク)/R-05(競合)が指摘 → 「個人ツール限定」と決めれば 4 リスクを一括解消
- **D-2**:再オープン = R-03(法的)。軽減:① 利用規約・プライバシーポリシー整備(`outputs/legal/`)、② 免責バナー強化(INV-BIZ-006「投資/移住助言ではない」明示)、③ Cookie 同意バナー(INV-BIZ-007、opt-in、anonymize_ip ON)
- **D-3**:選んだ = C(完全公開)。B(認証付き)ではない理由:ポートフォリオ用途で「URL を渡せばすぐ触れる」UX が必要 + 認証摩擦は逆効果
- **D-4**:INV-BIZ-006 = 金商法 / 不動産公正競争規約(投資・不動産助言ではない明示)、INV-BIZ-007 = 個人情報保護法 + Cookie 関連の電気通信事業法改正、INV-BIZ-008 = 利用規約・プライバシーポリシーへの導線(消費者契約法・特商法等)
- **D-5**:① 工数過大(同じものを 2 つ管理)、② 既存の Phase 0-8 成果物を再利用できる(DEC ログ・INV・テスト等が同じ知見の上に立つ)
- **D-6**:DEC = 「決まったこと」のログ(過去形)。GATE = 「ここで人間が判断する」要請(未決の意思決定ポイント)。分ける理由 = 判断「すべき」と「した」を混同しないため、未決のものを Gate として可視化して棚卸し可能に

- **F-3 イベント例**:① `view_change`(動線分析)、② `indicator_change`(関心分析)、③ `horizon_change`(将来志向の強さ)、④ `diagnosis_complete`(完走率)、⑤ `banner_click`(ホーム動線の人気)
- **F-4 3 ステップ**:① **外れた事実をそのまま記録**(都合の良い解釈を排除)、② 「なぜ外れたか」3 つ仮説立て(自分の前提が間違い / ユーザー像が違う / 計測の問題)、③ 次の打ち手を**新しい仮説**として書く(「治安より物価がクリックされた = ペルソナを物価重視層に絞り直す」)
- **F-5 ルール例**:① サンプル N < 100 では結論保留、② 単月ではなく 14 日以上の累積で判断、③ A/B 差が誤差範囲内なら「差なし」と結論、④ ユーザー数が極端に少ない指標は無視、⑤ **当初の仮説を後から書き換えない**(振り返り後に新しい仮説として記録)

## 🎓 取り組み方の推奨

### Round 1(初回・全 39 問)
- 各カテゴリ単位で **30 分 × 6 回 = 約 3 時間**
- 詰まった問題は解答ヒント + 参照ドキュメントで補強

### Round 2(1 週間後)
- A / E / F カテゴリだけ再走(理解の浅い部分を再確認)
- 解答を **口頭** で言う(脳の出力チャネルを使う)

### Round 3(月次)
- E カテゴリのピッチ系を録音 → 自分で聞き直す
- 友人 / 上司に説明してみる(リアル相手で詰まる箇所が判明する)

### Round 4(面接前・登壇前)
- E カテゴリ全 10 問を 1 分以内で回答できるか時間計測
