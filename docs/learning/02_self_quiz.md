<summary>🟢 初級 解答 + 解説</summary>

### A1. Streamlit を採用した理由

**ポイント**: Python だけで Web UI が完結 → 個人ツールとして最速の立ち上がり。

- 他の候補: **Dash**(Plotly 製)/ **Gradio**(AI デモ用)/ **Flask + React**(本格 Web)
- Streamlit を選んだ理由:
  - Python ファイルを **上から下に書くだけで動く**(コールバック地獄なし)
  - データ可視化(`st.plotly_chart` / `st.dataframe`)が標準装備
  - サイドバー・タブ・カラム等の UI 部品が即使える
  - 50-60 代向けの「動けば良い」レベルの UI に十分
- トレードオフ: スマホ最適化が弱い(別 CSS 対応必要)、複雑なインタラクションは苦手

### A2. DuckDB を選んだ理由

**ポイント**: 組込み DB(=ファイル 1 つで完結)+ OLAP に強い + Python 統合が良い。

- PostgreSQL との違い: サーバー不要、デプロイがファイルコピーで完結
- SQLite との違い: 列指向ストレージ(集計・分析が圧倒的に速い)、Parquet/CSV を直接 SELECT 可
- 個人ツールで「数百万件の取引データを集計」する用途にピッタリ
- 制約: 同時書込みに弱い(SaaS 化する時は PostgreSQL/Supabase に移行候補)

### A3. ARIMA と Prophet の使い分け

**ポイント**: それぞれの得意領域が違うので **アンサンブル**(両方使って良い方を採用)。

- **ARIMA**: 線形トレンド + 季節性、データ量少なくても動く、解釈しやすい
- **Prophet**: 休日効果、変化点(レジーム変化)、欠損に強い
- 本実装では両方を学習 → R² の高い方を採用 → 低ければ `no_prediction` で fallback

### A4. 偏差値 50 / 70 の意味

- **50** = 全国 47 都道府県の平均値そのもの
- **60** = 平均より良い(おおよそ上位 16%)
- **70** = 全国トップクラス(上位 2.3%)
- **30** = 全国の下位 2.3%
- 50 を境にして「平均より良い/悪い」を直感的に判断できるのが偏差値の良さ

### A5. 住みやすさスコア = 総合偏差値

**ポイント**: UX 上は「住みやすさスコア」、内部実装上は「総合偏差値」と呼ぶ。

- 50-60 代ユーザーに「偏差値」と言うと受験を想起させる → **「住みやすさスコア」と言い換え**
- 列ヘッダや表示には「住みやすさスコア(=総合偏差値)」と併記
- コード上の変数名・ロジックは `composite_score` のまま

### A6. なぜ偏差値化してから平均?

**ポイント**: 単位が違う指標を直接平均できない。

- 例: 物価指数 102(無次元) + 地価 937,111(円/㎡) を平均しても無意味
- **偏差値化**(平均 50、標準偏差 10)で全指標を共通スケールに正規化
- さらに「住みやすさ方向」(物価は低い方が良い)を反映 → 全指標が「数値が大きい=良い」に統一

### A7. API キーの取得難易度

| ソース | 発行 | 必要なもの |
|---|---|---|
| **e-Stat** | 即時(数分) | メアド + 用途記入 |
| **WAQI** | 即時(メール確認後数分) | メアド |
| **reinfolib** | **5 営業日待ち**(審査制) | 個人/法人区分 + 利用約款同意 |

→ プロジェクト計画では「reinfolib 待ち」を見越して並行作業の設計が必要

### A8. R² < 0.6 の扱い

**ポイント**: 信頼できない予測を堂々と出さない設計(R² ≥ 0.6 は INV-BIZ-003 という不変条件)。

- R² < 0.6 = 「実測の分散の 60% も説明できていない」= 雑な予測
- 該当する都道府県 × 時点の予測値は **`quality_status='no_prediction'`** に
- UI 上は 灰色塗り + 「予測対象外」のキャプション表示

### A9. 住みやすさ方向

**ポイント**: 指標ごとに「高い方が良い / 低い方が良い」が違う。

- **高い方が良い(HIGHER_IS_BETTER)**: 出生数 / 交通アクセス
- **低い方が良い(LOWER_IS_BETTER)**: 物価 / 地価 / 賃料 / 空気質(PM2.5) / 災害リスク
- ランキング計算では低い方が良い指標の偏差値を **-1 倍** して、全部「高いほど良い」に揃える

### A10. VSA(Vertical Slice Architecture)

**ポイント**: 機能(Usecase)単位でフォルダを切る。

- 従来のレイヤアーキ:
  ```
  controllers/ services/ repositories/ models/
  ```
- VSA:
  ```
  features/map_view/ ┬ usecases/ (show_map, show_ranking, ...)
                     ├ components/
                     └ data_provider.py
  features/data_pipeline/ ┬ usecases/ (fetch_external, run_batch, ...)
                          ├ sources/ (estat, mlit_*, env_soramame)
                          └ models/ (arima, prophet)
  ```
- メリット: 1 機能を消すとき関連ファイルが 1 フォルダに集まっている
- twin-build フローと相性が良い(各 Usecase が Phase 6 で設計される)

</details>

<summary>🟡 中級 解答 + 解説</summary>

### A11. データ信頼性の説明

**模範回答の骨子**:
1. **出典明示**: 各指標に e-Stat / 国土交通省 / WAQI 等の公的・公開データ源を明示
2. **最終更新日表示**: 「最終更新 2026-05-19」をデータ鮮度として明記
3. **モデル根拠タブ**: AI 予測モデルの R² と学習データ件数を透明化
4. **品質ゲート**: R² < 0.6 は予測無効化(no_prediction)で信頼できない数値を出さない
5. **無効化の補足**: 予測対象外都道府県は灰色塗り + キャプションで件数明示

### A12. SaaS 化のハードル

**3 大ハードル**:
1. **同時アクセス**: DuckDB は同時書込みに弱い → PostgreSQL / Supabase 移行
2. **個人情報・認証**: 移住タイプ診断の入力を保存する場合、PrivacyPolicy / GDPR / 改正個人情報保護法対応
3. **コスト構造**: 月額 980 円 × 100 人 = 売上 98,000 円。インフラ + API 利用料 + 開発工数の損益分岐を試算
- 副次: アラート・監視・SLA、サポート窓口、決済処理(Stripe 等)

### A13. 7 指標の選定根拠と代替

**なぜ 7 つ?**:
- 50-60 代の地方移住意思決定でよく挙がるトピックを **生活コスト / 環境 / 将来性 / 利便性** の 4 軸でカバー
- 多すぎると認知過負荷、少なすぎると差別化弱

**追加候補**:
- 医療(病院数 / 救急体制)
- 教育(学校数 / 大学進学率)
- 介護(高齢者施設数 / 介護費用)
- 気候(月別気温 / 降雪量)
- 文化(図書館 / 美術館 / 飲食店密度)
- 自治体支援金(移住補助 / 起業補助)
- インターネット環境(光回線普及率)

**「選定理由を語れること」自体が価値**: 顧客から「医療指標は?」と聞かれたら「v2 で追加予定、優先度はこう」と返せるか

### A14. e-Stat `13A01` の処理

**実コードの方針**:
- 当初は「area が `xx000` 形式の都道府県レベルのみ採用」
- 物価指数の area が `13A01`(東京都区部・県庁所在地ベース)で全部 reject されてしまった
- 修正: **「先頭 2 桁が 01-47 なら採用」** に緩和(例: `13A01` → `13`)
- 副作用: 同じ pref_code で複数値が来る → 「最新 time のレコードを採用」ロジックで対処

**学び**: API 仕様は実レスポンスを見ないと分からない。初手で 1 件 probe する習慣

### A15. reinfolib XCT001 事件の教訓

**何が起きた**:
- XCT001 を「不動産価格指数 = 賃料代理」と想定していた
- 実 API レスポンスは「地価公示の標準地データ」だった
- 賃料相場の代理としては不適切 → 別データソースを探す必要

**教訓**:
1. **API 名称と中身が一致しない場合がある**(マニュアルだけ読んで信用しない)
2. **MVP の前に必ず 1 件 probe**(JSON を実際に見る)
3. **代替候補を常に持つ**(住宅・土地統計調査 0004021429 で家賃階級加重平均で復旧)

### A16. 重み「全部 0」の挙動

**実コード**:
```python
positive = {k: float(v) for k, v in weights.items() if float(v) > 0}
total = sum(positive.values())
if total > 0:
    effective_weights = {...}  # 正規化
# total == 0 の場合は equal weight(等加重)にフォールバック
```

- 「全部 0」は実質的に「重み無効」= 等加重平均
- UI 上は警告ハンドリングなし → 仕様として割り切り

**改善余地**: 「全部 0」を選んだら警告メッセージ + 等加重ランキング表示の明示

### A17. 50-60 代向け UI の特徴

**変更点**:
| 観点 | 20-30 代向け | 50-60 代向け |
|---|---|---|
| フォントサイズ | 14-15px | **17-18px** |
| 行間 | 1.4-1.5 | **1.6-1.65** |
| ボタンタップ領域 | 32px+ | **44px+** |
| コントラスト | 中(おしゃれ重視) | **高**(WCAG AA 準拠) |
| 専門用語 | OK(偏差値、AQI 等) | **平易な言い換え**(住みやすさスコア) |
| アイコン | 控えめ | **多用**(💰🏘️🏠 等) |
| 操作 | スワイプ・ジェスチャー | **タップ + 大きい選択肢** |
| 文章 | 端的 | **「次は◯◯」のステップガイド** |

### A18. 「災害リスク」が実 API でない説明

**正直に言う**:
- 「災害リスクは国土数値情報(国土交通省公開データ)を **ローカルで集計** しています」
- 「リアルタイムの地震速報ではなく、長期的なハザードマップ集計値です」
- 「実 API(防災情報 XCT 等)への置き換えは v2 で検討」
- 隠さない → 信頼性は **透明性から生まれる**

### A19. ngrok vs Streamlit Cloud

| 軸 | ngrok | Streamlit Cloud |
|---|---|---|
| 公開期間 | 一時(8 時間) | 永続 |
| PC 起動 | 必要 | 不要 |
| URL | 毎回変動 | 固定 |
| 料金 | 無料(制限あり) | Free=Public/Private は $20/月 |
| 用途 | デモ・検証 | 本番運用 |
| データ更新 | ローカル DB が見える | CI で再デプロイが必要 |

**使い分け**:
- 顧客に「今ちょっと見せたい」= ngrok
- 公開アプリにする = Streamlit Cloud(or Render / Fly.io)

### A20. AI 予測精度が悪い時の UX

**3 段階の防御**:
1. **R² < 0.6 で no_prediction に fallback**(無効値を表示)
2. **UI で灰色塗り + 「予測対象外 N 県」の明示**
3. **モデル根拠タブで R²/MAE を透明化** → 「なぜダメだったか」を見せる
- これにより「AI が嘘をついた」と感じさせない
- 機械学習の限界を顧客に正直に伝える文化を作る

### A21. Plus 980 円の値付け根拠

**根拠の組み立て**:
1. **市場参照**: 田舎暮らしの本(月刊誌 1,500 円)、Smartie 移住(0 円)、移住相談会(無料)
2. **競合との差別化**: AI 個別推奨 + 月次更新データ + 物件連携 → 「年 12,000 円で人生の引っ越し選択を後悔しない」
3. **コスト構造**: e-Stat 無料、WAQI 無料、Claude API は 1 ユーザー月 10 回チャット = $0.5 程度 → 粗利率 90%+
4. **顧客の WTP(支払意思額)**: 移住失敗の損失(数百万円)に対して 1 万円は誤差
5. **段階的単価上昇**: Free → Plus 980 → Pro 2,980 で **3 倍ジャンプ** にすると Pro 比率が高まる(価格心理)

### A22. ペルソナ拡張(子育てファミリー)

**変わるもの**:
- **指標**: 出生数 → 学校数 / 保育園待機児童 / 公園面積 / 治安(犯罪率)を追加
- **重みデフォルト**: 子育てモード 〜 「教育 + 安全 + 自然」の優先
- **UI**: 子供の年齢入力 → 学齢別推奨(0-2 歳 / 3-5 歳 / 小学生 / 中高生)
- **コンテンツ**: 「子連れ移住経験者の声」コーナー、夏休み体験移住情報
- **B2C → B2B2C**: 自治体の子育て支援課と連携、企業の地方拠点設立とのバンドル

### A23. 競合との 3 つの違い

| 軸 | MoveMap | SUUMO 移住 | 田舎暮らしの本 | PLATEAU |
|---|---|---|---|---|
| **データ駆動** | 7 指標 × 偏差値 ✅ | 物件中心 | 取材中心 | 3D 地形のみ |
| **AI 予測** | 3/5/10 年先 ✅ | 無し | 無し | 無し |
| **個別最適化** | 診断 + 重み付け ✅ | 物件絞り込みのみ | 紙媒体 | 無し |
| **意思決定支援** | △(出口無し)| ◎(物件→契約)| × | × |

→ **差別化ポイント**: AI 予測 + 個別診断 + 統合スコア
→ **弱み**: 物件・情報量・取材

### A24. B2B SaaS の最有力顧客

**3 つの可能性**:
1. **自治体(移住促進課)**: 「自分の市町村が他県と比べてどう?」「人口流入予測」「移住者ターゲットの可視化」
   - 価格: 年契約 50〜200 万円
   - 顧客数: 全国 1,718 市町村
2. **不動産業者(地方支店)**: 「地域評価データ API」を物件サイトに組込み
   - 価格: 月額 5-10 万円
   - 顧客数: 中堅地方デベロッパー 50 社
3. **金融機関(地方銀行・信金)**: 地方支店戦略のための「地域成長性レポート」
   - 価格: 年契約 100-300 万円

**最有力は自治体**: 移住促進予算が確保されており、データ駆動の意思決定ニーズが高い

### A25. twin-build を一言で

**「AI 駆動開発のフェーズゲート + Coverage 管理を提供するフレームワーク」**

- 通常の開発: 各自が AI を使う → 設計と実装の整合性が崩れる
- twin-build: Phase 0〜8 で **各フェーズの成果物が前のフェーズに紐づく** ことを Coverage で機械的に検証
- 結果: AI に書かせても全体整合が取れる、人間は判断と Gate のみに集中

### A26. 個人情報最小化の例

- **DEC-005 個人ツール限定**: そもそも認証なし、ユーザー登録なし
- **API キーは .env 管理 + .gitignore 除外**: コミットに含まれない
- **診断回答は session_state のみ**: DB に保存しない
- **URL 共有は indicator/horizon のみ**: ユーザーの選択全部は URL に出さない
- **将来の SaaS 化に向けた検討事項**: 診断結果を DB 保存する場合のオプトイン同意、削除権

### A27. 1000 ユーザーまでのスケーリング

**段階別**:
1. **〜10 人**(現状): ローカル DuckDB + ngrok → 課題なし
2. **〜100 人**(MVP): Streamlit Cloud / Render に **read-only でデプロイ**(DB は週次更新)
3. **〜1000 人**: PostgreSQL に移行(同時アクセス耐性)、Cloudflare CDN で静的アセット配信
4. **〜10000 人**: Redis キャッシュで地図 fig をキャッシュ、Celery で月次バッチ非同期化

**ボトルネック予測**:

### A28. 自治体向けに人口流入予測

**逆方向の使い方**:
- ユーザーの「希望条件」(プロファイル)を 1 万人分集計 → どの県が選ばれるか
- 自治体A: 「2030 年に移住者 500 人を獲得するには、何の指標を改善すべきか」
- → **逆問題**: 観測データ(過去の人口流入)から、影響度の高い指標を回帰分析
- 必要なデータ追加: 自治体別人口移動統計(住民基本台帳人口移動報告)
- 自治体に売る KPI: 「公約に対する施策の有効性試算」

### A29. ChatGPT との違い

**「ChatGPT は質問しないと答えない、MoveMap は最初から比較できる」**

- ChatGPT は **対話型** → 全 47 県を一度に俯瞰できない、最新の数値は持っていない、地図表示なし
- MoveMap は **可視化 + データ + 予測 + 診断** が統合
- AI チャット相談機能を入れれば「**ChatGPT の利便性 + MoveMap のデータ基盤**」になる(差別化ポイント)
- 顧客への一言: 「ChatGPT は議論パートナー、MoveMap は意思決定ツール」

### A30. 次の 3 ヶ月で 1 つ機能追加するなら

**選ぶ機能**: AI 移住アドバイザー(Claude API でチャット相談)

**理由**:
1. **課金理由 No.1**: 「自分専用の推奨」が一番支払意欲を生む
2. **既存データを最大活用**: 7 指標 + 診断ロジック + 重み付けがそのまま使える
3. **実装が軽い**: Claude API + プロンプト設計 = 1〜2 週間
4. **PR 効果が大きい**: 「AI が移住先を提案」は記事化しやすい
5. **Pro プラン(2,980 円)の主機能になる**: 単価アップにも直結

**やらない理由がある機能**:

- 物件連携: アフィリエイト交渉が必要、技術的にはシンプルだが営業コスト
